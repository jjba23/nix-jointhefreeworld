/Everything I maintain, built by Nix: seven programs, seven Guile libraries, five Emacs packages, and the five packages nixpkgs does not have yet./

~nix-jointhefreeworld~ is a *Nix flake* that carries the whole
[[https://jointhefreeworld.org/][Jointhefreeworld]] collection in one place.  It is
not one ecosystem and not one language: there are *command-line programs* written
in Guile, *libraries* for Guile Scheme, *Emacs packages* written in elisp, and a
handful of *Guile dependencies* that nixpkgs has no packages for yet, which this
repository builds from the branches of a nixpkgs fork until upstream takes them.

Everything is pinned in the set's ~flake.lock~, so a consumer gets *one revision
that is known to build together*, instead of twenty-four separate URLs to keep in
step.

*If you run NixOS, nix-darwin or Home Manager and one of these projects is in your
stack, this is the URL you want.  If you use Guix, nothing here is required: the
same projects ship their own ~guix.scm~ and ~manifest.scm~, and this repository is
the Nix side of exactly those expressions.*

New here?  Jump to [[#quick-start][Quick start]] for the one command that answers
"does it work?", browse [[#what-is-here][What is here]] for the full inventory, or
read [[#use-it-from-your-own-configuration][Use it from your own configuration]] if
you already know you want it in your system.  Fixes, new packages and corrections
to this README are all welcome -- see [[#contributing][Contributing]].

* What you get
:PROPERTIES:
:CUSTOM_ID: what-you-get
:END:

- *Twenty-four packages from one URL*, at one revision.  ~#maak~,
  ~#guile-veritas~, ~#emacs-maak~, ~#guile-dbd-sqlite3~ and the rest all come
  from the same flake reference.
- *Every program is runnable without installing anything*: ~nix run~ works for
  all seven of them, with their ~meta.mainProgram~ and their descriptions set.
- *Granular by default.*  One overlay per package, a namespaced overlay, and a
  lazy ~packages~ set: asking for one package evaluates that one, so a project
  that breaks its own expression takes down itself and not the other twenty-three.
- *Take a part, not the whole.*  Two of the three flakes in this repository are
  reachable with ~?dir=~, so an Emacs configuration can fetch five small elisp
  repositories and never see a Guile dependency, or the other way round.
- *Builds described by their projects.*  Each package is built by the expression
  in its own repository -- the Guile ones' ~default.nix~, the elisp ones'
  ~default.nix~ next to the ~.el~ file -- so this repository never restates how
  something is built, and the two cannot drift apart.
- *Tests are run, not skipped.*  ~nix flake check~ builds every package of all
  three flakes and runs every Emacs ERT suite; CI does the same on every push.
- *Three platforms*: ~x86_64-linux~, ~aarch64-linux~, ~aarch64-darwin~.

** Which flake holds what
:PROPERTIES:
:CUSTOM_ID: which-flake-holds-what
:END:

There are three, each with its own ~flake.lock~, and the root one follows the other
two.  That is what makes it possible to take one part and never fetch the rest.

| flake        | what it is                      | what a consumer of it fetches               |
|--------------+---------------------------------+---------------------------------------------|
| root         | all of it                       | nixpkgs, fourteen projects, and both halves |
| ~guile-deps~ | the five packages nixpkgs lacks | nixpkgs and five nixpkgs branches           |
| ~emacs~      | the five Emacs packages         | nixpkgs and five small repositories         |

* Quick start
:PROPERTIES:
:CUSTOM_ID: quick-start
:END:

One command, no installation to undo, nothing added to your profile:

#+begin_src shell
nix run git+https://codeberg.org/jjba23/nix-jointhefreeworld#maak -- --help
#+end_src

That is the whole of it: the flake is fetched, ~maak~ is built against the
revision it pins, and you get its help text.  Swap ~maak~ for ~araneola~,
~ggg~, ~iter-vitae~, ~lambdock~, ~lenkesamler~ or ~mutastructura~ and you are
running the next program.

A library instead of a program is one word different:

#+begin_src shell
nix build git+https://codeberg.org/jjba23/nix-jointhefreeworld#guile-veritas
#+end_src

*** Before you start
:PROPERTIES:
:CUSTOM_ID: before-you-start
:END:

Flakes are still behind a flag in Nix 2.35, so either put

#+begin_src conf
experimental-features = nix-command flakes
#+end_src

in ~/etc/nix/nix.conf~, or pass
~--extra-experimental-features 'nix-command flakes'~ to the commands below.  There
is no ~codeberg:~ flake type; Codeberg is reached with a plain ~git+https~ URL,
which is what the examples use.  Nothing else is needed: no channel to add, no
overlay to copy, no build cache to trust.

** One part only
:PROPERTIES:
:CUSTOM_ID: one-part-only
:END:

~?dir=~ picks the flake inside the repository, and with it the inputs: an

#+begin_src shell

** Into Emacs
:PROPERTIES:
:CUSTOM_ID: into-emacs
:END:

The Emacs packages are packages in the Emacs sense, so they are asked for through
the scope the overlay extends -- ~pkgs.emacsPackages~ -- and ~withPackages~ builds
an Emacs that has them on its load path, autoloads and all:

#+begin_src nix
{ pkgs, ... }: {
  environment.systemPackages = [
    (pkgs.emacsPackages.withPackages (epkgs: [
      epkgs.maak
      epkgs.veritas
      epkgs.modusregel
      epkgs.tekengrootte
      epkgs.welkomscherm
    ]))
  ];
}
#+end_src

The snippet assumes the set's overlay is already applied to ~pkgs~, which is what
[[#use-it-from-your-own-configuration][the next section]] is about: without it,
~pkgs.emacsPackages~ knows none of these names.  Take one package and it is one
line; take none and nothing changes.  ~emacsPackages.withPackages~ is what honours
~pkgs.emacsPackages~, so this is also the expression to use in a plain flake shell,
where the same call is enough to get an Emacs with the package in it.

* Use it from your own configuration
:PROPERTIES:
:CUSTOM_ID: use-it-from-your-own-configuration
:END:

Add the overlay once and the packages are available from ~pkgs~ as if nixpkgs had
them, built against the revisions this flake pins.

#+begin_src nix
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  inputs.nix-jointhefreeworld.url = "git+https://codeberg.org/jjba23/nix-jointhefreeworld";

  outputs = { self, nixpkgs, nix-jointhefreeworld, ... }: {
    nixosConfigurations.example = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        ({ pkgs, ... }: {
          nixpkgs.overlays = [ nix-jointhefreeworld.overlays.default ];

          environment.systemPackages = with pkgs; [
            guile-veritas
            maak
          ];
        })
      ];
    };
  };
}
#+end_src

Home-manager takes the same overlay, through ~nixpkgs.overlays~ in the NixOS module
you already import, or ~pkgs~ inherited from it; nothing here is NixOS-specific
except that the packages need the platform to be one of the three in
[[#what-is-built-where][What is built where]].

** Three ways to take it
:PROPERTIES:
:CUSTOM_ID: three-ways-to-take-it
:END:

| what you write                                                     | what you get                                   |
|--------------------------------------------------------------------+------------------------------------------------|
| ~nixpkgs.overlays = [ nix-jointhefreeworld.overlays.default ];~    | every name, replacing nixpkgs' copies          |
| ~nixpkgs.overlays = [ nix-jointhefreeworld.overlays.maak ];~       | one name, and nothing else added               |
| ~nixpkgs.overlays = [ nix-jointhefreeworld.overlays.namespaced ];~ | ~pkgs.jointhefreeworld.maak~, nothing shadowed |

There is a per-package overlay for every name in the repository -- ~overlays.maak~,
~overlays.guile-veritas~, ~overlays.guile-dbd-sqlite3~ and so on.  Each builds
against the set's own definitions, so ~overlays.araneola~ finds its ~guile-scriba~
even though only ~araneola~ is added to your ~pkgs~, and
~overlays.guile-dbd-sqlite3~ finds its ~guile-dbi~.

The Emacs half is an overlay for the Emacs package scope rather than for ~pkgs~, so
it has an output of its own:

#+begin_src nix
let
  emacsPackages = pkgs.emacsPackages.overrideScope nix-jointhefreeworld.emacsOverlay;
in
  emacsPackages.withPackages (epkgs: [ epkgs.maak ])
#+end_src

Two things worth knowing about the overlays:

- ~overlays.default~ *replaces* the nixpkgs package of the same name.
  ~guile-scriba~ in ~pkgs~ becomes this revision of scriba rather than the one
  nixpkgs ships, which is the point -- but it also means anything else in your
  system built against the older copy is rebuilt against this one.  The
  per-package and namespaced overlays do not have that effect.
- Whether a package supports your platform is decided by its own ~meta.platforms~,
  and it is enforced in the checks rather than by leaving an attribute out: on
  darwin, ~pkgs.lambdock~ exists and refuses to build, which is how nixpkgs
  behaves too.  Asking for it there is an error, not a missing attribute.

* Keeping up to date
:PROPERTIES:
:CUSTOM_ID: keeping-up-to-date
:END:

#+begin_src shell
nix flake update                           # move every input of the set
nix flake update maak lambdock             # move two of them
nix flake update guile-deps emacs          # re-pin a part, with its own inputs
nix flake check                            # build all of it
#+end_src

~flake.lock~ is the release: whoever consumes the set pins a revision of it, and
gets exactly the project revisions listed there.  A new tag in one of the projects
is picked up by updating that one input, which is a one-line change with a hash in
the diff you can read.

There are three locks, and they overlap: the root pins the inputs of both parts as
well as its own, so ~nix flake update~ there moves the whole set.  Running it
inside ~guile-deps~ or ~emacs~ moves only the pins that a ~?dir=~ consumer of that
part gets; the set keeps what its own lock says until you update it there too.
Editing a part's ~flake.nix~ is picked up by the set as it is read, since a path
input is pinned by its path rather than by its content.

:PROPERTIES:
:CUSTOM_ID: what-is-built-where
:END:

| system           | what happens                                                 |
|------------------+--------------------------------------------------------------|
| ~x86_64-linux~   | everything                                                   |
| ~aarch64-linux~  | everything                                                   |
| ~aarch64-darwin~ | everything that supports darwin (~lambdock~ is wayland-only) |

* How it is put together
:PROPERTIES:
:CUSTOM_ID: how-it-is-put-together
:END:

- Three flakes, two of them followed by the root through relative path inputs, and
  ~inputs.nixpkgs.follows~ on both so that the three share one nixpkgs instead of
  pinning one each.
- One ~input~ per project, with ~flake = false~: only the source tree is wanted,
  not the project's own flake and its lock file.
- One table, ~sources~ in [[./flake.nix][flake.nix]], mapping a package name to the
  input and the expression inside it.  The names are the ones nixpkgs would use
  (~guile-veritas~, not ~veritas~), so the overlay replaces rather than duplicates.
- The overlays call ~final.callPackage~, not ~nixpkgs.callPackage~.  That single
  choice is what lets one package here depend on another: ~araneola~ needs
  ~guile-scriba~, and in a set of its own that has to be the sibling, not whatever
  nixpkgs happens to have.
- ~packages~ is a plain lazy attribute set: asking for one package evaluates that
  one, so a project that breaks its own expression takes down itself and nothing
  else.  ~checks~ is where the whole set is forced -- that is a check's job, and it
  is also where ~lib.meta.availableOn~ decides which packages exist on the platform.
- ~apps~ is derived from ~meta.mainProgram~ for the seven programs.  The names are
  listed rather than discovered by filtering every derivation, so that ~nix run~
  does not force the whole set either.
- Each package also has an overlay of its own, and ~overlays.namespaced~ puts all
  of them under ~pkgs.jointhefreeworld~ without shadowing anything.  Both build
  against a ~pkgs~ extended with the set's definitions, so a single name still
  resolves its siblings, while your ~pkgs~ only gains the name you asked for.

The Emacs packages are built the same way, by an expression in each package's own
repository: a ~default.nix~ next to the ~.el~ file, called from the commit the
~emacs~ flake pins.  The same file builds the package in its own checkout with
~nix-build~, so the expression is worth having without this repository, and each
library's README says so.  Each one uses ~melpaBuild~, the builder MELPA itself
uses, so an install gets the ~-pkg.el~, the autoloads and the byte code and
~(require 'maak)~ works.  The version is read from the ~;; Version:~ header of the
file itself, inside that repository's expression, so a release is one edit there
and nothing here can fall behind.  The ~emacs~ flake puts them into ~emacsPackages~
with ~overrideScope~ -- ~melpaBuild~ comes from that scope and ~lib~ is passed in,
since the scope does not carry it -- and the root follows the flake; the scope is
derived from ~prev~ rather than ~final~ in the root's overlay, since defining it in
terms of itself would not terminate.

The checks in ~emacs~ run each ERT suite, from a copy of the source tree -- the
store is read-only and Emacs writes its native-compilation cache under ~HOME~ -- so
a green ~nix flake check~ means the elisp was compiled and its tests passed.  The
root's checks merge them, so one command covers all three flakes' worth of packages.

~lambdock~ carries one small override.  Its test suite treats GTK's "cannot resolve
icon 'utilities-terminal'" warning as fatal, and a bare build sandbox has no icon
theme to resolve it from; the overlay adds ~adwaita-icon-theme~ to its
~nativeCheckInputs~ so the tests still run.  It goes away when the project's tests
bring their own icons.

* Adding a project
:PROPERTIES:
:CUSTOM_ID: adding-a-project
:END:

Which of the three shapes it is decides where the expression goes.

** A Guile project with an expression of its own
:PROPERTIES:
:CUSTOM_ID: a-guile-project-with-an-expression-of-its-own
:END:

Three steps, all in [[./flake.nix][flake.nix]]:

1. Add the repository as an input:
   #+begin_src nix
   inputs.example = { url = "git+https://codeberg.org/jjba23/example"; flake = false; };
   #+end_src
2. Add the package to ~sources~, with the expression to call inside that repository:
   #+begin_src nix
   guile-example = { repo = "example"; expr = "default.nix"; };
   #+end_src
3. Lock and check:
   #+begin_src shell
   nix flake lock
   nix flake check -L
   #+end_src

** A dependency nixpkgs does not have
:PROPERTIES:
:CUSTOM_ID: a-dependency-nixpkgs-does-not-have
:END:

It goes into [[./guile-deps/flake.nix][guile-deps/flake.nix]], as an input and a
~sources~ entry, and the root picks it up through the ~guile-deps~ input it already
follows.  It has to come from a branch that a pull request can merge, so that the
entry can be deleted later.  Add its name to ~depNames~ in the root flake as well,
so that ~packages~ lists it.

** An Emacs package
:PROPERTIES:
:CUSTOM_ID: an-emacs-package
:END:

The expression goes into the package's own repository as ~default.nix~, next to the
~.el~ file: a ~pname~, the version read from the ~;; Version:~ header,
~src = lib.cleanSource ./.~, ~files = ''("*.el")''~, and the pieces of ~meta~ a
package needs.  ~cleanSource~ is not decoration -- ~melpaBuild~'s unpack hook reads
a path ending in ~.el~ as "one .el file", so a checkout directory by that name
would not be found.  Here it is an input in [[./emacs/flake.nix][emacs/flake.nix]] and
a line in ~srcs~; an ERT suite goes into ~suites~ there too, and the checks will
run it.  Add its name to ~elispNames~ in the root flake so that ~packages~ lists it
as ~emacs-<name>~.

* Contributing
:PROPERTIES:
:CUSTOM_ID: contributing
:END:

Contributions are welcome, and they do not have to be code.  A package that does
not build on your machine, a platform that is missing from a ~meta.platforms~, a
sentence in this README that is not true any more -- all of those are worth an
issue.

- *Packaging bugs* -- something in this repository does not evaluate, a
  ~?dir=~ consumer gets the wrong inputs, an overlay shadows more than it should:
  open an issue or a pull request on
  [[https://codeberg.org/jjba23/nix-jointhefreeworld][the Codeberg repository]].
- *Bugs in a project* -- the crash is in ~maak~ or ~lambdock~ itself, not in how it
  is packaged: each project has its own repository, linked from the tables in
  [[#what-is-here][What is here]], and that is where its expression lives too, so a
  fix can be tested with ~nix-build~ in the checkout before this repository is
  touched.
- *New packages* -- [[#adding-a-project][Adding a project]] is a checklist of what
  a new entry needs; an issue saying "this project should be in the set" is enough
  to start.
- *Patches* -- please run ~nix flake check~ before opening the pull request.  It
  builds every package of all three flakes and runs every elisp test suite, which
  is exactly what CI will run, so a green local run means a green pipeline.  The
  style of the Nix files here is the style of the rest of the collection: comments
  that explain *why* a choice was made, and expressions that defer to the project's
  own build rather than restating it.

Documentation fixes are merged as quickly as code, and a good bug report is more
valuable than a hasty patch -- there are no silly questions.

* Continuous integration
:PROPERTIES:
:CUSTOM_ID: continuous-integration
:END:

Woodpecker runs [[./.woodpecker/ci.yml][.woodpecker/ci.yml]] on every push and
pull request: one ~nixos/nix~ container that runs ~nix flake check~ three times,
once per flake.  The set's run builds every package of all three and runs every
Emacs test suite; the other two cover the locks that a ~?dir=~ consumer of that
part would get.  A project that breaks its own expression, or an input that moves
under the set, is caught there instead of by whoever installs next.  The badge at
the top of this page is that pipeline.

There is no binary cache yet, which means a fresh install compiles the Guile
bytecode on the machine doing it.  The packages are small and the compilation is a
second or two each; if it becomes a nuisance, a Cachix cache plus a push step in
that pipeline is the usual answer, and ~nix flake check~ already builds everything
it would need to push.
