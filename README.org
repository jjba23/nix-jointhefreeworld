*NIX-PACKAGES* — the Guile libraries and applications I maintain, in one flake: one command to install any of them, one overlay to put them all in a NixOS or home-manager configuration.

Repository: [[https://codeberg.org/jjba23/nix-packages]]

Every Guile package here is built with the expression that lives in its own project, so nothing is restated in this repository and the two cannot disagree about how a program is compiled. The Emacs packages are the exception, and the only one: their repositories have no expression, so theirs is written here.

In ~packages~ they appear with an ~emacs-~ prefix (~emacs-maak~, ~emacs-veritas~, ...), which is what makes ~nix build .#emacs-maak~ and ~nix flake show~ reach them; the overlay is the interface an Emacs configuration actually wants.

* Install

Flakes are still behind a flag in Nix 2.35, so either put

#+begin_src conf
experimental-features = nix-command flakes
#+end_src

in ~/etc/nix/nix.conf~, or pass ~--extra-experimental-features 'nix-command flakes'~ to the commands below. There is no ~codeberg:~ flake type; Codeberg is reached with a plain ~git+https~ URL, which is what the examples use.

** One program

#+begin_src shell
nix profile install git+https://codeberg.org/jjba23/nix-packages#maak
maak --version
#+end_src

The same URL works for the rest of the set: ~#araneola~, ~#guile-bewaking~, ~#guile-hygguile~, ~#guile-kracht~, ~#guile-olive-css~, ~#guile-orgwebalchemy~, ~#guile-scriba~, ~#guile-veritas~, ~#iter-vitae~, ~#lambdock~, ~#lenkesamler~ and ~#mutastructura~.

** Try one without installing it

#+begin_src shell
nix run git+https://codeberg.org/jjba23/nix-packages#maak -- --help
nix build git+https://codeberg.org/jjba23/nix-packages#guile-veritas
#+end_src

~nix run~ works for the six packages that install a program (~araneola~, ~iter-vitae~, ~lambdock~, ~lenkesamler~, ~maak~, ~mutastructura~); the libraries are meant to be built and to land on Guile's load path through a shell or a system configuration.

** Into Emacs

The Emacs packages are packages in the Emacs sense, so they are asked for through the scope the overlay extends — ~pkgs.emacsPackages~ — and ~withPackages~ builds an Emacs that has them on its load path, autoloads and all:

#+begin_src nix
{ pkgs, ... }: {
  environment.systemPackages = [
    (pkgs.emacsPackages.withPackages (epkgs: [
      epkgs.maak
      epkgs.veritas
      epkgs.modusregel
      epkgs.tekengrootte
      epkgs.welkomscherm
    ]))
  ];
}
#+end_src

Take one and it is one line; take none and nothing changes. ~emacsPackages.withPackages~ is what honours ~pkgs.emacsPackages~, so this is also the expression to use in a plain flake shell, where the same call is enough to get an Emacs with the package in it.

* Use it from your own configuration

The point of the set is the overlay: add it once and every package below is available from ~pkgs~ as if nixpkgs had them, built against the revisions this flake pins.

#+begin_src nix
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  inputs.nix-packages.url = "git+https://codeberg.org/jjba23/nix-packages";

  outputs = { self, nixpkgs, nix-packages, ... }: {
    nixosConfigurations.example = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        ({ pkgs, ... }: {
          nixpkgs.overlays = [ nix-packages.overlays.default ];

          environment.systemPackages = with pkgs; [
            guile-veritas
            guile-scriba
            maak
          ];
        })
      ];
    };
  };
}
#+end_src

Home-manager takes the same overlay, through ~nixpkgs.overlays~ in the NixOS module you already import, or ~pkgs~ inherited from it; nothing here is NixOS-specific except that the packages need the platform to be one of the three in [[*What is built where][What is built where]].

Two things worth knowing about the overlay:

- It *replaces* the nixpkgs package of the same name. ~guile-scriba~ in ~pkgs~ becomes this revision of scriba rather than the one nixpkgs ships, which is the point — but it also means anything else in your system built against the older copy is rebuilt against this one.
- A package that cannot exist on your platform is simply absent (~lambdock~ on darwin), and a consumer that names it there gets a normal "attribute missing" error rather than a build that cannot work.

* Keeping up to date

#+begin_src shell
nix flake update                          # move every input
nix flake update maak lambdock             # move two of them
nix flake update maak-el welkomscherm-el   # an Emacs package's repository
nix flake check                            # build all of them
#+end_src

~flake.lock~ is the release: whoever consumes the set pins a revision of it, and gets exactly the project revisions listed there. A new tag in one of the projects is picked up by updating that one input, which is a one-line change with a hash in the diff you can read.

* What is built where

| system          | what happens                                                  |
|-----------------+---------------------------------------------------------------|
| ~x86_64-linux~  | everything                                                    |
| ~aarch64-linux~ | everything                                                    |
| ~aarch64-darwin~| everything that supports darwin (~lambdock~ is wayland-only)   |

~x86_64-darwin~ is deliberately absent: nixpkgs 26.11 dropped it, so listing it would make evaluation fail for everyone rather than for that one platform.

* How it is put together

- One ~input~ per project, with ~flake = false~: only the source tree is wanted, not the project's own flake and its lock file.
- One table, ~sources~ in [[./flake.nix][flake.nix]], mapping a package name to the input and the expression inside it. The names are the ones nixpkgs would use (~guile-veritas~, not ~veritas~), so the overlay replaces rather than duplicates.
- The overlay calls ~final.callPackage~, not ~nixpkgs.callPackage~. That single choice is what lets one package here depend on another: ~araneola~ needs ~guile-scriba~, and in a set of its own that has to be the sibling, not whatever nixpkgs happens to have.
- ~packages~ filters each result through ~lib.meta.availableOn~, so a package's own ~meta.platforms~ decides where it appears.
- ~checks~ is ~packages~ plus the Emacs test suites, so ~nix flake check~ builds the whole set and runs the elisp tests.
- ~apps~ is derived from ~meta.mainProgram~: a package that installs a program gets an ~apps~ entry, a library does not.

The Emacs packages are the one part whose expressions are written here, in [[./emacs.nix][emacs.nix]], because those repositories have no expression to call: an elisp library is a single file, and the build is the same shape every time. They use ~melpaBuild~, the builder MELPA itself uses, so the installed package gets its ~-pkg.el~, its autoloads and its byte code. The version is read from the ~;; Version:~ header of the file itself, so a release is one edit there and this repository cannot fall behind.

The overlay puts them into ~emacsPackages~ with ~overrideScope~, and the scope is derived from ~prev~ rather than ~final~: it is being defined in terms of itself, which would not terminate. Each one is also listed in ~packages~ under an ~emacs-~ prefix so that it can be built on its own.

~checks~ also runs each Emacs package's ERT suite, from a copy of the source tree — the store is read-only and Emacs writes its native-compilation cache under ~HOME~ — so a green ~nix flake check~ means the elisp was compiled and its tests passed.

~lambdock~ carries one small override. Its test suite treats GTK's "cannot resolve icon 'utilities-terminal'" warning as fatal, and a bare build sandbox has no icon theme to resolve it from; the overlay adds ~adwaita-icon-theme~ to its ~nativeCheckInputs~ so the tests still run. It goes away when the project's tests bring their own icons.

* Adding a project

Three steps, all in [[./flake.nix][flake.nix]]:

1. Add the repository as an input:
   #+begin_src nix
   inputs.example = { url = "git+https://codeberg.org/jjba23/example"; flake = false; };
   #+end_src
2. Add the package to ~sources~, with the expression to call inside that repository:
   #+begin_src nix
   guile-example = { repo = "example"; expr = "default.nix"; };
   #+end_src
3. Lock and check:
   #+begin_src shell
   nix flake lock
   nix flake check -L
   #+end_src

If the project needs something nixpkgs does not have, that dependency goes in as an input and a ~sources~ entry too, exactly like the five above — and it has to come from a branch that a pull request can merge, so that the entry can be deleted later.

An Emacs package is the other shape, because there is no expression to call:

1. Add the repository as an input, the same way.
2. Add it to ~emacs.nix~, which takes a ~pname~, the ~.el~ file the version is read from, the source, and the three pieces of ~meta~ that a package needs. If it has an ERT suite, add it to ~suites~ in [[./flake.nix][flake.nix]] too, and ~nix flake check~ will run it alongside the rest.
3. Lock and check.

* Continuous integration

[[./.forgejo/workflows/ci.yml][.forgejo/workflows/ci.yml]] runs ~nix flake check~ on every push and pull request, in the ~nixos/nix~ image on Codeberg's runners. That builds every package and runs every Emacs test suite, so a project that breaks its own expression — or an input that moves under the set — is caught there instead of by whoever installs next.

There is no binary cache yet, which means a fresh install compiles the Guile bytecode on the machine doing it. The packages are small and the compilation is a second or two each; if it becomes a nuisance, a Cachix cache plus a push step in that workflow is the usual answer, and ~nix flake check~ already builds everything it would need to push.
